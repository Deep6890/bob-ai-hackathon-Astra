AeroReady — System Engineering Analysis

IBM BoB Hackathon · Senior Engineering Review · Full codebase investigation

1. Current System Architecture

The project is a predictive maintenance dashboard for turbofan engines (NASA C-MAPSS data). It has three layers:

Frontend

React 18 + Vite + TailwindCSS. SPA with client-side routing via state. AppDataContext is the single global data store — all API calls are centralised there. api.js validates every response before it enters state. Recharts for charts, lucide-react for icons.

Backend

Flask 3 + SQLAlchemy 2 + SQLite (app.db). Clean layered architecture: Routes → Controllers → Services → Repositories → Models. Flask-Migrate for schema migrations. Flask-CORS enabled globally. Served by Waitress in production.

ML Engine

Two pre-trained artifacts loaded at startup: LSTM (best_rul_lstm.pth) for RUL regression, and Isolation Forest (multivariate_iforest.pkl) for sensor health. Both run via the PredictiveMaintenanceCopilot class. No training at runtime — inference only.

Database (SQLite)

6 tables: assets, sensor_readings, predictions, sensor_analysis, missions, readiness_results. FK cascades are defined correctly. A composite index exists on (asset_id, time_cycles). SQLite file lives in src/backend/app.db.

3. Backend → ML Model Flow

PipelineService.analyze_engine(engine_id) → SensorRepository (load all readings for engine) → Build pandas DataFrame (14 sensor columns) → PipelineHandler.analyze_engine(df, engine_id) → ModelHandler.get_copilot() (singleton) → PredictiveMaintenanceCopilot.analyze_asset(id, df) → _predict_rul() [LSTM] + _assess_current_health() [IsolationForest] → Returns (rul, sensor_health_dict, latest_cycle) → AnalysisRepository.save_analysis() → DB persist

For mission readiness: after analyze_engine, PipelineService.evaluate_mission_readiness computes margin, risk flag, readiness score, and recommendation using static formulas on ReadinessResult — no second ML call.

4. ML Input / Output

LSTM — RUL Predictor

  • Input: 30-cycle sliding window × 14 smoothed sensor features (sensor_2,3,4,7,8,9,11,12,13,14,15,17,20,21)
  • Pads with zeros if <30 cycles available
  • Architecture: 2-layer LSTM (hidden=64), FC: 64→32→ReLU→Dropout→1
  • Output: Single float — RUL in cycles (clipped to ≥0)
  • Test R²: 0.865, MAE ~11.3 cycles

Isolation Forest — Health Monitor

  • Input: Last 5-cycle window × 14 scaled sensor features
  • Reference: Healthy baseline (RUL > 100 in training)
  • Output per sensor: state (NORMAL / DEGRADING / ABNORMAL / UNKNOWN), anomaly_score, persistence, slope, normalized_deviation
  • State logic: persistence ≥ 60% + strong deviation (>3σ) + trend alignment
Bug: In pipeline_service.py line 47–54, sensor_9_smooth and sensor_14_smooth are hardcoded to 0.0 ("Not in schema, fallback to 0"), even though both columns exist in the SensorReading model and are populated during ingestion. This introduces silent bias into every LSTM prediction. The model was trained on real sensor_9 and sensor_14 values.

7. Features That Are Only Partially Implemented

  • ⚠ PARTIAL AI Copilot Page — renders structured analysis from the ML pipeline correctly, but is labeled "AI Copilot" and "Bot" in the sidebar. There is NO LLM, no conversational interface, and no IBM watsonx integration. It is a read-only structured display panel, not a copilot.
  • ⚠ PARTIAL Fleet Table "Inspect" button — calls onNavigate('Asset Health', row.unit) but Fleet.jsx receives no onNavigate prop from App.jsx (the prop is never passed). The button renders but does nothing.
  • ⚠ PARTIAL Sidebar "Predictive Insights" nav item — exists in assetNavItems but the App.jsx switch block has no case for "Predictive Insights"; it falls to default which renders PredictiveInsights, so it accidentally works. But it was clearly intended to route to PredictiveInsights and there's no explicit route — just a fallthrough.
  • ⚠ PARTIAL Upload progress feedback — after upload, a hardcoded 3-second delay is used to wait for background analysis, then refetches. No real backend progress polling exists — analysis could take longer for 100 engines.
  • ⚠ PARTIAL Mission system — Mission rows are created/updated by the readiness endpoint as mock data (SORTIE-{engine_id}). There is no UI to create, name, schedule, or manage missions independently. All missions have the same hardcoded 30-cycle duration from the frontend constant.
  • ⚠ PARTIAL Fleet page "Inspect" navigation — FleetPage receives an optional onNavigate prop, but in App.jsx the Fleet page is rendered as <FleetPage /> with no prop, so the Inspect column always shows nothing functional.
  • ⚠ PARTIAL submission.yaml — completely empty. All required hackathon metadata fields (team name, track, problem statement, solution summary, key features, tech stack) are blank placeholders.

8. Missing Integration Points

  • No real LLM / IBM watsonx integration — The "AI Copilot" is pure structured data display. No natural language query, no explanation generation, no LLM anywhere.
  • No backend progress endpoint for CSV processing — frontend polls with a fixed 3s sleep after upload; no GET /api/v1/data/status exists.
  • Fleet → Asset navigation is broken — FleetPage calls onNavigate('Asset Health', row.unit) but App.jsx passes no onNavigate or onSelectEngine to the Fleet page render. A user cannot navigate from Fleet table to a specific engine.
  • No error boundary in React — a validation throw in api.js or a render error will crash the entire app without a recovery UI.
  • No health check used by frontend — GET /api/v1/health and GET /api/v1/system/status exist but the frontend never polls them. The "System Online" dot in the header is a static hardcoded green dot.
  • No authentication / authorization — any client can reset the dataset, upload any file, or read any engine data.
  • No DB migrations applied automatically at startup — flask db upgrade must be run manually; no call in run.py or container entrypoint.

9. Bugs and Technical Risks

BUG (HIGH) — sensor_9 and sensor_14 zeroed in pipeline_service.py
Lines 47 and 51 in pipeline_service.py hardcode sensor_9_smooth: 0.0 and sensor_14_smooth: 0.0 with the comment "Not in schema, fallback to 0". Both columns exist in the SensorReading model and are populated during ingestion. This corrupts every single LSTM prediction silently. The fix is trivial: r.sensor_9_smooth and r.sensor_14_smooth.
BUG (HIGH) — Fleet Inspect button is broken
Fleet.jsx calls onNavigate('Asset Health', row.unit) on click, but App.jsx renders <FleetPage /> with no onNavigate prop. The button is a no-op for all 100 engines.
RISK — success_response does not wrap data
responses.py does return jsonify(data) — no { "data": ... } wrapper. api.js has unwrap logic (json.data !== undefined ? json.data : json) that silently falls through correctly. But if a future route accidentally returns a dict with a "data" key, the unwrap will strip the outer shell incorrectly. Not currently broken, but a silent footgun.
RISK — Background analysis thread has no completion signal
The frontend waits a hardcoded 3 seconds after CSV upload then refetches engines. For a 100-engine fleet, background analysis (100 ML inference calls) may easily take 10–30+ seconds. The UI will show stale "Unavailable" data until the user manually refreshes.
RISK — ReadinessResult has unique constraint on mission_id but per-analysis predictions accumulate
Each CSV upload creates a new Prediction row per engine (no limit). After many uploads, get_latest_prediction picks the newest one correctly, but ReadinessResult is upserted by mission_id. Since only one Mission exists per asset, this works — but is fragile if mission logic changes.
RISK — Missing 500 error handler
register_error_handlers handles APIError and 404, but generic Python exceptions from ML inference (e.g. CUDA OOM, missing .pth file) will surface as raw Flask 500 responses with Python tracebacks in the body.
RISK — SensorAnalysis backref conflict
sensor_analysis.py uses db.backref("sensor_analyses", ...) on Prediction, while analysis_repository.py uses a manual SensorAnalysis.query.filter_by(prediction_id=pred.id). The backref relationship is declared with lazy="dynamic" and cascade="all, delete-orphan" — this duplicates the cascade already declared on Prediction's readiness_results relationship. Not currently broken, but confusing and fragile.

11. How IBM Bob Can Be Meaningfully Integrated

The system has rich, real, structured ML outputs that are perfect fodder for an LLM layer. Here are the most impactful integration points, ordered by value and feasibility:

Option A (Highest Value) — Natural Language Fleet Q&A via IBM Bob
Replace the current "AI Copilot" page with a real conversational interface powered by IBM Bob. The context payload to Bob would be the structured JSON already returned by POST /mission/readiness and GET /engines/{id}/sensors for the selected engine. Bob can explain sensor anomalies, justify the RUL prediction, suggest maintenance actions, and answer "why is this engine grounded?" in natural language. This is achievable in a few hours with the Bob API + a backend proxy endpoint.
Option B — Automatic Narrative Report Generation
Add a "Generate Report" button to the Reports page. On click, the frontend sends the full fleet summary (all missionReadinessById data) to a new backend endpoint POST /api/v1/reports/narrative. The backend formats a structured prompt and calls IBM Bob to generate a fleet-wide health narrative (paragraph form). The result is displayed as a text report that can be copy-pasted for briefings.
Option C — Sensor Anomaly Explanation
In the SensorDrawer component (Asset Health page), add an "Explain with AI" button. Clicking it sends the sensor's state, persistence, normalized_deviation, slope, and degradation_direction to a backend endpoint that queries IBM Bob. Bob returns a 2–3 sentence plain-English explanation of what the anomaly means in the context of turbofan degradation. This is a highly targeted, high-quality UX improvement that directly uses the sensor evidence the ML engine produces.
Option D — Maintenance Priority Justification
On the Maintenance page, an "AI Justification" panel uses IBM Bob to explain why the ML pipeline assigned HIGH/MEDIUM/LOW priority, given the sensor states and RUL margin. This addresses the black-box concern that is central to ML in safety-critical domains — a key differentiator for hackathon judges.

Recommended Integration Architecture

Frontend "Explain" button → POST /api/v1/copilot/explain (new Flask route) → Backend builds structured context from DB (sensor states, RUL, readiness) → Backend calls IBM Bob API with prompt + context → Returns natural language text to frontend → Displayed in a clean panel (streaming optional)

Key design principle: IBM Bob should receive structured, pre-computed ML evidence as context — not raw sensor numbers. The ML pipeline already does the hard work; Bob provides the natural language explanation layer on top. This architecture is honest, grounded, and avoids hallucination of technical values.
